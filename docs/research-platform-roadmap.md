# MySciAgent：从现有工具到多智能体科研协作平台

## 定位与目的

MySciAgent 是面向个人研究生的多智能体科研协作平台。以真实课题为中心，连接已经使用的应用、资料与计算环境，让文献研究、方案设计、代码实现、实验执行、结果分析和知识积累连续推进。

平台复用现有工具：论文仍在文献库，笔记仍在知识库，代码仍在 Git 仓库，实验仍在指定计算环境运行。平台维护任务、关联关系和执行记录，把结果写回原应用。不会要求用户把全部资料迁入新的聊天工作台。

设计目标来自本次需求：统一入口；多个专业 Agent 协作；接入现有应用；Paper2Code；科研实验与仓库管理；高能力模型负责思考、设计和审查，DeepSeek 等低成本模型负责具体实现、测试执行和结果整理。

| 组件 | 对应科研环节 | 必须保留的能力 | 处理决定 |
|---|---|---|---|

| zhixun-agent | 水文领域数据查询和业务问答 | 通用科研流程不要求水文专用助手；具体课题需要相应数据工具 | 延后；按真实水文课题接入已有数据/API/脚本，之后再包装领域 MCP，不为复制旧架构单独实现一个助手 |
| server-monitoring | 算力状态、实验运行跟踪 | 实验任务的提交状态、日志、退出码、取消和结果记录 | 这些是核心实验能力，应通过本地进程或 SSH/实际调度器适配实现；团队全套服务器监控可后置，二者不能混为一谈 |
| yuque_mcp_server | 阅读笔记、实验结论和研究积累 | 能读取原笔记、按需写回并记录来源/版本 | 已有个人源码优先；核对可用接口后修复部署适配，或直接使用语雀 API。写回功能须单独实现和验证；不再把取得特定上游 commit 作为产品建设前提 |

### 最小产品的建设优先级

1. 登记真实应用、课题仓库、数据与计算环境，提供论文/笔记的可靠输入，跑通一次结果写回。
2. 建立课题、任务和产物协议，打通高能力模型规划、DeepSeek 执行、工具验证和关键审查。
3. 完成 Paper2Code、独立代码工作区、实验提交与跟踪、结果分析及可追溯归档。
4. 在真实使用中增加自动论文获取、日报、通用服务器监控和水文专用工具。

每个组件只负责清晰的一类能力。新实现先放在合适的现有组件或平台适配层；形成独立可复用服务后再拆仓库，避免为了仓库名称提前制造空项目。

当前 repositories.json 的 `required_for_default_stack` 仍描述未改造的上游默认启动配置。它不等于目标科研平台的必需功能清单。需要在后续最小部署改造中同步调整 Compose、启动脚本、工具注册、清单和测试；本次仅更新产品决策，不宣称依赖阻塞已经消除。

## 协作架构

```text
Web / 消息应用 / 编码助手
             |
      课题与任务协调层
      任务图、依赖、审批、预算、事件
             |
      模型路由与专业 Agent
 文献 | 规划 | 编码 | 验证 | 实验 | 分析
             |
      统一工具注册与应用适配
 MCP / API / CLI / 文件 / SSH / 必要时 UI 自动化
             |
  现有文献库、笔记、Git 仓库、计算环境、实验记录
```

协调层是共享事实与任务状态的来源。跨框架协作先采用明确的任务输入/输出和持久化事件；不能依靠几个机器人互相自由聊天来保证交付。

| Agent | 负责内容 | 主要交付与验收 |
|---|---|---|
| 文献 Agent | 检索、阅读、证据提取和相关工作整理 | 来源链接/文献 ID/页码，区分原文结论和推断 |
| 规划与审查 Agent | 高能力模型推理、研究设计、关键代码与结论审查 | 方案、假设、验收条件、决策理由和待确认事项 |
| 实现 Agent | DeepSeek 等低成本模型按规格编码、补充文档与测试 | 独立分支、补丁、测试结果和实现差异 |
| 验证与实验 Agent | 检查规格、运行测试、提交实验、跟踪资源和故障 | 原始命令、退出码、Run ID、日志及失败分类 |
| 分析与记录 Agent | 程序计算指标、整理图表、归档和周报 | 可追溯结果、结论证据、下一步候选任务 |

测试执行和指标计算由工具完成，模型负责组织与解释。关键实现由独立审查步骤检查，结论必须指向实际运行结果。

## 模型分工与任务协议

默认采用“高能力模型设计 → DeepSeek 执行 → 工具验证 → 高能力模型关键审查”。模型名称、服务端点和每类任务预算均配置化，不把平台绑定到某个供应商。Codex/Claude Code 是可选执行工具，不因工具名称就假定其实际后端模型。

任务必须包含 `project_id`、`task_id`、目标、输入资源引用、依赖任务、执行器、允许操作、输出格式、验收条件、时间/Token/费用预算。产物回执包含代码 commit、命令、退出码、测试报告、日志/指标位置、模型与版本，以及未解决问题。

重试次数与预算可配置。重复失败、规格冲突、证据不足时升级到规划/审查步骤；达到上限进入等待处理状态。发布、对外发送、付费计算和重要数据变更采用对应任务的确认策略。

## Paper2Code 的完整流程

| 步骤 | 工作 | 验收 |
|---|---|---|
| 方法规格 | 读取论文，列公式、输入输出、模块、超参数、数据拆分和评价指标 | 每条关键设定能定位到论文或明确标为待确认 |
| 实现设计 | 高能力模型确定范围、模块映射、基线和资源预算 | 人能审阅，缺失数据/算力提前列出 |
| 代码实现 | 执行模型在独立 worktree 编码，优先复用许可允许的官方实现 | 单元/接口测试、最小可运行样例、环境记录 |
| 实验验证 | 先小样本 smoke test，再基线、主实验、消融和多种子实验 | 独立测试集、统一比较条件，记录失败结果 |
| 复现报告 | 对照论文结论，记录复现差距、实现偏差和不确定性 | 代码、数据、配置、指标均可追溯；不以“运行成功”代替复现成功 |

## 科研仓库与实验组织

平台仓库 `mysciagent` 负责协调和集成；依赖组件留在个人同名仓库，各研究课题使用独立研究仓库，避免把所有科研代码和数据塞进平台。

```text
research-project/
  research/       # 问题、文献映射、方案、决策与复现差异
  src/            # 课题代码
  tests/          # 验证
  configs/        # 基线、实验、消融和种子配置
  reports/        # 可审阅的结果、图表与说明

workspace-data/<project_id>/<run_id>/
  manifest.json   # commit、环境、数据版本/指纹、配置、模型与费用
  logs/
  metrics/
  artifacts/      # 大文件另存并登记位置，不默认提交 Git
```

每个编码任务创建分支或 worktree，验收后合并；并行任务不共用可写工作区。实验记录关联不可变的代码 commit、环境锁定文件、数据拆分、参数、随机种子及产物摘要。记录支持多个种子 Run 汇总为同一个实验，不丢弃失败记录。先接现有实验记录工具，确实没有时再实现最小注册表。

## 五阶段落地顺序

### 阶段 0：个人仓库和依赖基线（本次工作）

交付：复制平台和可访问依赖，保留历史与许可证，记录来源/commit/可用性；切换组件获取地址；提交本规划。继承栈的原样部署仍有依赖缺口；下一步围绕最小科研流程裁剪部署配置，为缺失组件实现最小替代接口。估计部署前核对需 1–2 个工作日；替代实现按实际接口范围另行拆分，不再等待全部上游源码到齐。

验收：仓库可读取；已复制 refs/提交一致；已有 dailyinfo 不被覆盖；依赖检查能明确报告未就绪项。当前状态见迁移记录。

### 阶段 1：接入真实资源，完成第一次日常流程

先登记真实使用的论文、笔记、代码、服务器和消息入口；优先只读工具，再按需要开放写回。用一个入口和一个执行器跑通“从已有收藏找相关论文 → 写阅读笔记 → 创建待办”。预计 3–5 个工作日，不含外部账号授权等待。

验收：使用真实收藏；来源可回查；重复执行不重复入库；结果进入用户原应用；取消、连接失败和重试都有记录。

### 阶段 2：统一任务与多模型协作

实现课题档案、任务图、模型路由、结构化任务交接及事件记录；接入高能力规划模型、DeepSeek 执行模型和独立验证工具；随后再扩展第二个 Agent 框架。预计 5–7 个工作日。

验收：一个真实任务经历规划、执行、测试、审查；每步可定位到模型/工具/产物；失败能暂停、重试或升级；费用与耗时可统计。

### 阶段 3：Paper2Code 与实验仓库闭环

选一篇与当前课题有关、数据和算力可取得的论文，完成方法规格、独立工作区、代码实现、小样本验证和基线对比。接入真实本地或远程计算环境及实验注册表。预计 7–10 个工作日，论文复杂度和实验耗时单列。

验收：从论文到代码、Run、结果表可双向追溯；可复跑基线；服务器断连、任务失败能恢复跟踪；复现差异如实记录。

### 阶段 4：稳定的个人科研工作台

汇总课题进度、阅读队列、任务、实验和待确认事项，提供日报/周报；逐项增加领域工具与应用适配。先持续使用两周再决定扩展范围；此阶段不承诺一次接入所有应用。

验收：真实日常任务完成率、人工接管次数、结果可追溯率、每任务成本与人工操作耗时可统计；阈值先测基线再确定。

## 首个验收场景

“从我的文献收藏中选一篇与当前课题相关的方法论文，生成带来源的方法笔记和实现计划；确认后在指定研究仓库新建分支，用 DeepSeek 完成最小实现并运行测试；提交一个小规模实验，把代码版本、环境、数据和指标关联起来，最后把结果写回研究笔记，并提出下一步建议。”

这是贯穿五个阶段的主线。先把这一条真实流程做完整，再扩大应用数量与自动化范围。
