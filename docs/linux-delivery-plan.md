2026-10-15 通过已有 SSH 配置只读核对了运行 hydromodel 的服务器：Linux；`/home/zlh/hydromodel` 存在；系统 Python 为 3.8，uv 已有 3.11/3.12；Podman 3.4.2 可用，未发现 Docker、podman-compose 或 docker-compose。可见 GPU 型号不代表当前可独占或已有空闲算力，首次部署不自动启动训练。

首版环境选择：复用 uv 的独立 Python 3.12 环境；可在服务器本地进程中先运行科研协调和执行接口。Agent Host 的容器方案评估 Podman 兼容性后再确定，不直接假定旧 Podman 可运行现代 Docker Compose 的全部构建配置，也不默认升级共享服务器。

现有 hydrosystem 已提供 `Study → Trial → validation evidence` 任务语义，以及 XAJ 率定、模拟和 NSE/KGE 评价接口。MySciAgent 应通过 adapter 调用这些能力，RunRecord 保存领域 study/trial/evidence 引用；不复制参数率定、数据访问和指标实现。首次只读核对现有结果，再选择一条获确认的轻量基线执行。首次运行该接口前仍需核对服务器上的实际安装版本和数据。

## 第一版产品与使用体验

用户通过一个现有消息入口提出：“读取指定论文和代码，设计一个改进实验，确认后运行，把结论写回我的研究笔记。”

系统返回方案、执行进度和证据链接。用户可以查看当前课题、待确认任务、正在运行的实验、失败原因及下一步建议。先提供 CLI/消息入口和真实记录，随后再决定是否需要单独开发 Web 界面。

## 具体模块和代码归属

| 模块 | 负责什么 | 实现与归属 |
|---|---|---|
| Agent Host | 对话、任务理解、工具调用、消息入口 | 首版只启用一个 Hermes 实例；继承的其他实例/框架按实际需要后加 |
| ResearchOps | 课题、任务状态、交接、预算、审批、候选决策和恢复 | 在 mysciagent 新增 `research_ops/`；以 SQLite 保存状态，MCP/API 提供给 Agent Host |
| Research Worker | 在隔离工作区中规划/编码/审查，调用合适模型和工具 | 新增 `research_ops/workers/`；模型和编码执行器使用适配器，支持高能力规划与 DeepSeek 实现 |
| Experiment Runner | Git worktree、环境、命令、日志、指标、超时/取消及远程任务 | 新增薄 `research_ops/runners/`；水文任务优先适配现有 hydrosystem；先服务器本地执行，后按需要接 SSH/Slurm |
| Resource Adapters | 论文、笔记、仓库、文件及消息通知 | 复用个人 mylibrary/dailyinfo/yuque 仓库；新增适配器只补缺失接口 |

前四项角色不是四个独立数据库或四套聊天系统。第一版可用 ResearchOps API + 后台 worker 两个进程共享事务数据库；实验任务单独子进程运行。应用原始数据继续由各应用管理，大产物放文件目录。

## 服务分组

| 分组（待实现配置） | 包含 | 验收目的 |
|---|---|---|
| personal | 一个 Agent Host、必要的个人工具、个人数据持久化 | 用户能真实对话并调用已配置工具 |
| research | ResearchOps、worker、runner，连接 personal | 用户能提交、跟踪并复查实验 |
| optional | 语雀/文献/情报/云盘等按应用实际情况启用 | 未配置项显示未启用，不阻止不依赖它的任务 |
| team | 团队公共 bot 与共享工具服务 | 日后确实需要团队访问再部署，首版个人科研流程不依赖它 |

这些是后续新部署配置的分组，当前继承的 docker-compose.yml 尚未完成此拆分。部署时使用独立 Compose project 名称、数据根目录和可配置端口，不默认复用原作者路径、内网端点或身份。

## Linux 服务器目录约定

```text
~/code/mysciagent/              # 平台配置与协调实现
~/code/<个人组件仓库>/          # 文献、情报、笔记等可复用组件
~/research/<课题仓库>/          # 实际科研代码
~/mysciagent-data/
  state/research.sqlite         # 课题/任务/Run/事件
  workspaces/<task_id>/         # 独立 worktree
  runs/<run_id>/                # 日志、指标、产物和运行清单
  memory/                      # 研究摘要及引用索引
```

上述为推荐目录，部署配置允许更改。数据路径与服务权限须在服务器预检中确认；第一条实验应是指定工作区内的轻量基线，避免直接修改现有科研工作区。

## 五个版本：每个版本都有可用结果

### v0.1：先让个人助手在服务器上工作

开发：拆出最小部署配置和启动入口，按启用服务检查依赖，关闭未配置工具；选择一个消息入口与真实模型，支持一次工具连接自检。缺失的仓库统计、论文下载、团队水文服务不应成为个人版的启动依赖。

验收：服务健康检查通过；真实模型回复；成功读取指定项目文件和一个真实资料来源；重启后配置与数据保留；未启用工具清楚显示状态。不能把“进程启动”当作“模型和工具可用”。

### v0.2：把一次真实实验交给平台

开发：ResearchProject、ExperimentSpec、RunRecord、事件接口；runner 接指定代码基线和环境，执行固定命令并采集退出状态、日志、指标；支持查询和取消。先由人提交方案，避免调度和模型推理同时引入不确定性。

验收：一次真实基线可以从提交运行到结果归档；数字可定位到原始文件；失败有原因；断连后可继续查看；已有代码工作区不会被混用。

### v0.3：高低成本模型协作与有限研究循环

开发：高能力模型给出方案和验收条件，DeepSeek 等执行模型按规格修改独立工作区，工具测试与评测后交关键审查；实现接受/拒绝/修复/升级/停止及预算上限。候选与评测器分开管理。

验收：同一基线下至少展示成功改进、没有改进和运行失败的处理路径；记录每次候选的代码、资源、模型和原始结果。未获得真实改进时如实结束，不预设效果指标。

### v0.4：Paper2Code 与方法工具化

开发：论文解析为方法规格；已有实现先复现并封装工具，缺实现再按模块补代码；检查论文设定、参考输出和完整实验结果。工作流借鉴 PaperCoder/Paper2Agent，组件复用按实际试验决定。

验收：指定论文的方法、代码、测试、Run 和复现差异可关联；一个已验证方法能在第二个任务中再次调用。代码能执行与论文结果复现分别验收。

### v0.5：完整日常科研工作台

开发：接入用户实际文献、笔记、情报、任务和服务器，回写结论、整理周报、处理人工反馈；需要更广搜索时，再在相同任务与预算下试验一种进化引擎。

验收：以一个真实课题连续使用，检查人工接管、失败恢复、证据追溯、总成本和有效研究结果；根据实际使用决定新增 UI、其他 Agent 或团队访问。
